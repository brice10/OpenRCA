Comme décrit plus haut, nous souhaitons se servir des données de base du dataset OpenRCA pour créer un dataset de scénarios d'adaptation. De base le dataset OpenRCA fournit des failures cases, nous souhaitons les compléter pour décrire des scénarios d'adaptation complets. Selon notre représentation, un scénario d'adaptation est à minima décrit par 3 éléments principaux à savoir: 

- L'observation: qui décrit une dynamique sur une métrique ou un ensemble de métriques qui cause un défaillance ou est susceptible de causer une défaillance dans le future (ex: augmantation soudaine du cpu, disque plein ...). Pour le problème d'adaptation, l'observation est la description implémentable d'une cause potentielle à un problème en se servant des métriques. Nous allons remplir manuellement cette colonne observation en fonction des détails extraits dans les logs, métriques et traces.

- La cause: description compréhensible par l'humain de la logique métier ayant induit l'observation. Ex: une cause à l’augmentation soudaine du cpu peu être une promotion sur le site, la cause d'un pic de trafic peut également être une promotion sur le site, la cause d'une saturation de l'espace de stockage peut être un nombre l'incription de nouveaux utilisateurs etc. Une cause rajoute des informations contextuelle à une observation. Nous allons rédiger manuellement la cause à partir de l'observation, des logs, métriques et traces.

- Les actions d'adaptation: décrit les actions à effectuer pour mitiger la défaillance identifiée, elle peut être curative ou préventive  dépendamment de l'observation. Par exemple si on observe un disque saturé, l'action d'augmenter l'espace du disque est curative par contre si on observe une réduction progressive de l'espace de stockage avant saturation, l'action d'augmentation est préventive. De même les action d'adaptation doivent être associées à un score de priorité: par exemple si on observe un mauvais cache hit/miss ratio signifiant que le cache fonctionne mal et induisant un temps de traitement de requêtes plus long et donc une saturation du cpu, une action visant à corriger le fonctionnement du cache serait prioritaire à une action visant à faire du scaling par exemple,

Ensuite les scénario d'adaptation doivent avoir d'autres colonnes pour décrire: la nature de la défaillance qui peut être réseau, infrastructure ou application. les métriques extraites, les logs et/ou les traces qui justifient l'observation faite et une description compréhensible par l'humain qui présente le scénario d'adaptation complet.

Par exemple on pourrait avoir un fichier d'heuristique qui associe la colonne reason des failure cases de base aux patterns de filtrage des données contextuelles à extraire ex: si failure reason c'est high memory usage dans les logs, métriques et traces n'extraire que les données qui on un rapport avec la mémoire.

Le script construit pourra étre exécuté pour générer par dataset, ou pour tout les datasets, un fichier plus complet de failure cases nommé record_detailled.csv.
